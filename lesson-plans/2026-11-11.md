# Lesson Plan: 2026-11-11

## The project: a standalone OpenAI-shaped client

The [`harness-gateway-client`](https://github.com/cppalliance/runvil/tree/master/crates/harness-gateway-client) crate is how a Host sends model rounds to the Runvil Gateway. Under the Gateway parts it is an OpenAI-shaped chat client. It builds the request, reads the streamed reply, and classifies failures. That is useful on its own: someone writing a Rust AI pipeline who only needs a little inference should be able to use it without Runvil.

The class will turn it into that product, maybe in its own repository. The rules from the [2026-11-10 lesson plan](2026-11-10.md) still apply: learn first, write it yourself, push every day.

## Goals

1. **Any endpoint.** It works with third-party OpenAI-compatible inference endpoints, not only the Gateway.
2. **No Runvil.** It depends on no Runvil crate, so anyone can use it.
3. **Clean public API.** A stranger can read it and use it.
4. **Deslopped implementation.** The inventory below is the starting list.
5. **Streaming.** A reply can arrive in pieces, and the API handles that on purpose.
6. **Room for multimodal.** Images, audio clips, and video. This is low priority. Do not build it, but do not design it out.
7. **Written down.** Documentation that explains how it works, and every design decision recorded with its rationale.

## Decisions to make

Each one gets written down: the options, the choice, and why.

1. **Where does the trait live?** The Harness reaches the client through the `InferenceBroker` trait (`models` and `chat`), which Runvil defines. The new crate cannot name it. Either the trait moves, or Runvil keeps it and a small adapter implements it over the new client.
2. **Whose types?** The crate uses 59 items from `runvil`: `Message`, `ToolSchema`, `ToolCall`, `Completion`, `CompletionOptions`, `Error`, `ErrorCode`, the metrics, and the model catalog. Either they move into the new crate, or it defines its own and Runvil converts.
3. **What assumes the Gateway?** Find all of it. Some to start with: the model list parser skips any model with no `context` field, which a stock OpenAI model list does not have. `thinking` is sent as `chat_template_kwargs.enable_thinking`. The environment variables are `RUNVIL_GATEWAY_URL` and `RUNVIL_GATEWAY_API_KEY`. Keyless access follows the Gateway's loopback rule. The type names say `Gateway`.
4. **What happens to search?** `GatewaySearch` calls the Gateway's own `/tools/web_search` relay and implements a trait from `plugin-web`. It is our thing, not an OpenAI thing. Does it stay in Runvil, move to its own crate, or become something general?
5. **What shape is streaming?** Today every request streams. The caller passes a callback that receives text and reasoning pieces, tool calls are held back until they are whole, and the finished reply comes back at the end. Should it return a stream instead? Should non-streaming requests exist? How does a caller cancel?
6. **What does a message hold?** The Engine's `Message` already keeps content as JSON, either a string or an OpenAI content-parts array. The new crate needs a message type that can grow image, audio, and video parts later.
7. **What is public?** 14 items are public today and only 5 are used outside the crate. Decide the smallest surface a stranger needs.
8. **Where does it live, and what is it called?** Its own repository or not. "Gateway" no longer fits the name.
