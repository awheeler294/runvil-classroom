# Lesson Plan: 2026-11-17

## The project: ten pieces of Runvil

This is the list of what is left to build in Runvil. When items 1 through 9 are done and subagents work, Runvil is feature complete. Item 10 is further out. Nobody builds it yet, and it is on the list so that people start thinking about it.

Each item gets one owner. The rules from the [2026-11-10 lesson plan](2026-11-10.md) still apply: learn first, write it yourself, push every day. We review plans, not code.

## How the items connect

- **Item 5 is the highest-value item on the list.** Every check and guardrail we add pays off again each time an AI writes code for us. It also touches every repository.
- **Item 8 comes before item 9.** Subagents give the model the ability to launch tasks. Tasks have to be airtight first, so that any bug found while building subagents is in the new code and nowhere else.
- **Items 6, 7, and 8 need the same thing:** a record of a run's effects and events that can be written out, read, and compared. The recorder stores it, the Host's debug mode writes it to a file, and the golden tests compare it. Those three owners should talk early and try to agree on one format.
- **Item 2 reaches the client as its second step.** Whoever owns item 3 designs for more than one protocol from the start.
- **Item 4 feeds item 6.** The command-line check of a prompt should use the strong checker.

### 1. Tool metadata, like MCP

Difficulty 1. Owner: Sean.

A tool should be able to announce what it does, such as whether it writes files or whether it uses the internet. The idea comes from MCP, where a tool can have annotations. The reason we want it is prompts. If a prompt can describe itself the same way, a prompt can be published as an MCP function. A prompt already has the right input: one JSON object, checked against the parameters it declares under `args:`. It already has the right output: a string, which can be structured JSON. The metadata is the only piece missing. There is a little design work here, and it is not hard.

**Where it stands**

- A prompt's front matter accepts a fixed set of keys: `name`, `description`, `runvil`, `max_tool_iterations`, `uses`, `args`, `models`, and `prompts`. None of them says what the prompt does to the world.
- A Plugin's tool declares a name, a wire name, a description, and a parameter schema, and nothing else. See `RvToolInfo` in the Plugin contract.
- The Harness's `ToolInfo` has four more flags: `structured_output`, `survives_stop`, `describes_tools`, and `model_only_call`. A library Plugin cannot set them, and the model never sees them.
- A tool written inside a prompt with `tools.adhoc` accepts exactly three keys: `name`, `description`, and `parameters`.
- The MCP Pack keeps a server tool's name, description, and input schema. It never reads the server's `annotations` or `outputSchema`.
- The decision page lists "Filters and labels" as planned work: labels on `ToolInfo`, modeled on MCP's.

**Open**

- Which labels? MCP's four hints are the starting point: `readOnlyHint`, `destructiveHint`, `idempotentHint`, and `openWorldHint`.
- Where does a prompt declare its metadata?
- Does a prompt declare its labels, or does the Engine work them out from the tools the prompt uses?
- How do a Plugin tool's labels cross the Plugin contract?
- Is a label a hint, or does something enforce it?

**Read first**

- [`ToolInfo`](https://github.com/cppalliance/runvil-harness/blob/master/crates/runvil-internal/types/src/tools/info.rs) in the Harness
- [`RvToolInfo`](https://github.com/cppalliance/runvil-plugin-api/blob/master/crates/runvil-plugin-sys/src/lib.rs) in the Plugin contract
- [Tools and Packs](https://github.com/cppalliance/runvil-harness/blob/master/decisions/tools-and-packs.md), the decision page

### 2. Vendor chat completions

Difficulty 2. Owner: Justin.

Today Runvil speaks one inference protocol, the OpenAI shape of chat completions. It is the most basic one. To really work with Anthropic's and OpenAI's models, Runvil has to speak each vendor's own protocol. Anthropic is the example: its replies hold signature blocks, and those have to be kept and sent back.

**Decided**

The work goes in this order:

1. A proxying endpoint in the Gateway.
2. The Gateway client. There may not be much to do there.
3. The Engine. It needs changes, and they are not big.

**Where it stands**

- The Gateway has one upstream protocol. Its `Protocol` type has the single variant `Openai`, and it forwards a request's body as it is, with only the model name changed.
- No Runvil code speaks a vendor's own protocol yet.
- The client reads reasoning text out of a reply and never sends it back.
- The client sends the thinking switch as `chat_template_kwargs.enable_thinking`. The decision page lists the reason for that as an open question.
- Some groundwork is done: a message's content is already JSON, so a message can hold data.

**Open**

- Which endpoint does the Gateway expose for each vendor, and what does it change on the way through?
- What does the Engine have to keep in a message so that a signature block survives a round trip?
- How does a prompt stay the same no matter which vendor runs it?
- Which vendor comes first?

- [The Gateway's one upstream](https://github.com/cppalliance/runvil-gateway/blob/master/crates/gateway/protocol/src/upstream/openai.rs)

### 4. Lua lint and AST check during parse

Difficulty 2. Owner: Jason.

We write our own parser for Lua. It does not compile to bytecode. It checks the syntax and builds a syntax tree, called an AST. Libraries that do this already exist, and they are heavy. This parser goes in the Engine, and the Engine avoids heavy dependencies, so we do not use them.

What it buys us: today the parse of a prompt stops at the first error and does not check in depth. With a tree, the Engine can really check a prompt and report every error and every warning in one pass. We want to know that a prompt has a problem up front, not hours into a run after the tokens are spent. The command-line check of a prompt (item 6) uses the same checker.

**Where it stands**

- `Prompt::parse` compiles every Lua block through `mlua`, which is Lua 5.5. A syntax error fails the parse and points at the right line of the prompt. The parse returns one error.
- There are no warnings.
- `mlua` hands back a compiled function. It exposes no tree.
- Mistakes past syntax show up only when the code runs: a global that does not exist, a misspelled function such as `prompt.sectoin`, a wrong number of arguments, a section path that names no section, an `execute` of a name that `prompts:` does not list.
- One check is already waiting for a tree. The parser leaves `require` calls unchecked, because checking them needs each block's syntax tree.
- `RESERVED_NAMES` lists every global the Engine provides. Nothing lists the functions of each global in one place.
- No Lua parser or linter crate is a dependency today.

**Open**

- The parser has to accept exactly what Lua 5.5 accepts. How do we test that it agrees with the real compiler?
- Which checks come first?
- What is an error, and what is a warning?
- How does `Prompt::parse` return a list of problems where it returns one error today?
- How does the checker learn the Engine's Lua API: the names, and how many arguments each function takes?

**Read first**

- [How a Lua block is compiled today](https://github.com/cppalliance/runvil-harness/blob/master/crates/runvil-internal/lua/src/program.rs)
- [`Prompt::parse`](https://github.com/cppalliance/runvil-harness/blob/master/crates/runvil-internal/prompt/src/parse.rs)
- [The reserved names](https://github.com/cppalliance/runvil-harness/blob/master/crates/runvil-internal/lua/src/globals.rs)

### 5. Static build checks and guardrails

Difficulty 2. Owner: Greg K. This is the highest-value item on the list.

Every static check and guardrail we add multiplies, because it works every time an AI writes code. It is very important to get right, and it changes every repository. It needs one owner for hygiene across all the repositories. The owner has to know `xtask`, and the owner writes the documentation that says what the rules for each repository are.

**Where it stands**

- Every repository runs `cargo fmt`, one strict clippy lint table, and rustdoc with warnings as errors. Past that, each repository runs a different set.
- `runvil-harness` has the most. `cargo xtask tidy` there checks, among other things, the product boundary, the unsafe allowlist, the size of types, and the shape of a facade crate.
- The check code is shared by copying. `type_size.rs` exists in five repositories, and the `build-checks` crates in `runvil-plugin-std` and `runvil-plugin-bashkit` are identical. A fix in one copy does not reach the others.
- The repositories disagree in places. The Gateway enforces a 500-line limit on files, and the Harness's `AGENTS.md` says a file has no length limit.
- Several rules in the Harness's `AGENTS.md` seem to have no check behind them, such as the ban on `thiserror` and the ban on inline `mod`.
- About ten rows of the [slop inventory](2026-11-11.md#slop-inventory) are things a mechanical check could have caught: ticket ids in comments (row 7), a hand-written `Debug` over a secret that already redacts itself (row 15), and attributes that do nothing (row 17).

**Open**

- Does the check code live in one shared crate, or do the copies stay?
- Which rules are the same in every repository, and which belong to one?
- Which new checks come first?

**Read first**

- [The smallest set of checks](https://github.com/cppalliance/runvil-plugin-bashkit/blob/master/crates/build-checks/src/lib.rs), in `runvil-plugin-bashkit`

### 6. Standalone command-line Host

Difficulty 1 to start, then 2. Owner: Justin.

A reference Host that runs a prompt from the command line. It is possible now because a prompt's input and output are settled: one JSON object goes in, and one result comes out. Getting a basic one running is easy. It becomes a 2 when it grows Plugins, a directory of prompts, more options, and the debug log.

What it is for: tests on CI that run a prompt and inspect what happened, and people trying out their own prompts.

**Decided**

- You name the prompt on the command line.
- An option points at a directory, and the `PromptFinder` looks there for the prompts that `execute` names.
- The result goes to standard output, or to a file with an option.
- Arguments come as `key=value` pairs, which the Host builds into the JSON object, or from a file that holds the JSON.
- A debug mode writes every event and every effect to a file.

**Where it stands**

- No official repository has a command-line Host. The nearest thing is the `run-prompt` example in the `runvil` crate, which runs one prompt held in a constant against an offline broker.
- This repository has three student Hosts: [Kirill's runner](../students/kirill/runner/src/main.rs), [Mateo's Host](../students/robles/host/src/main.rs), and [Andrew's Host](../students/wheeler/host/src/main.rs). Kirill's runs a prompt end to end against the Gateway, on an older version of the API.
- Between them, the three write the same setup code more than once: a timer, an offline broker, a finder, and a `Host` built by hand.
- The Harness now ships stock finders: `FindTextPrompt`, `FindFilePrompt`, and `PromptSet`, which can load a directory. It ships no stock timer.
- [Andrew's notes](../students/wheeler/building-a-host-wtf.md) list what was hard to work out.

**Open**

- Plugins. They are probably compiled in. Which Packs does the Host hold?
- What happens with a prompt that takes user input?
- Does it have a mode that only checks a prompt (item 4)?
- Where does it live?

**Read first**

- [The `run-prompt` example](https://github.com/cppalliance/runvil-harness/blob/master/crates/runvil/examples/run-prompt.rs)
- [The `runvil` crate's root](https://github.com/cppalliance/runvil-harness/blob/master/crates/runvil/src/lib.rs), which walks through what a Host does

### 7. Recorder and replay, in a `runvil-hosts` repository

Difficulty 2, maybe 3. Owner: Kirill.

There is functionality that every Host will probably want, and not every Host will want the same pieces. A new repository, `runvil-hosts`, is the home for it. The first piece is the database recorder, which writes the record of a run to a SQLite database, and replay, which runs a recorded run again from that record.

This one is important. The whole architecture depends on replay working, and nobody has shown that it works. Showing that it works is the first job, because a problem found here would reach the whole design.

**Where it stands**

- The recorder exists today inside Workshop, as the `workshop-run-log` crate. It implements the Harness's `RunRecorder` trait and stores every effect, answer, and event of a run in two tables, `runs` and `records`.
- It uses Turso, an engine compatible with SQLite, and writes a file named `runs.db`.
- It depends on no other Workshop crate, so it can be lifted out.
- Replay is not built. The decision pages describe it as planned work: a driver in the Harness starts a run from the recorded seed and start time, feeds the recorded answers back to the Engine, and compares what comes out.
- The claim that replay tests is determinism. With the same seed, the same clock, and the same answers in the same order, the Engine emits the same effects, events, and ids.
- On a replay no tool runs. The recorded results are fed back. That is why a tool may keep no state between calls.
- One known hole: a tool's file operations are not in the record yet. The decision to make each one an effect is made, and the code is not written.

**Open**

- What does a passing replay prove, and which runs go in the first test?
- How does the recorder leave Workshop? It has an `agent` column that is Workshop's, and Workshop pins the Turso version.
- Does `runvil-hosts` get a facade crate, one crate that a Host depends on for all of it? In the Harness the word "facade" has a strict meaning, a crate made only of `pub use` lines, and a check enforces it.
- How do the pins stay in step? Workshop would pin two repositories that have to agree on one commit of `runvil`.

**Read first**

- [The recorder](https://github.com/cppalliance/runvil-workshop/blob/master/crates/workshop/run-log/src/lib.rs) in Workshop
- [The `RunRecorder` trait](https://github.com/cppalliance/runvil-harness/blob/master/crates/harness-internal/runner/src/recorder.rs)
- [Tasks and fanout](https://github.com/cppalliance/runvil-harness/blob/master/decisions/tasks-and-fanout.md), the decision page, for determinism and for replay under planned work
- [Testing and debugging](https://github.com/cppalliance/runvil-harness/blob/master/decisions/testing-and-debugging.md), the decision page
- [The Harness and the Host API](https://github.com/cppalliance/runvil-harness/blob/master/decisions/harness-and-host.md), the decision page, for what a recorder receives

### 8. Tasks testing

Difficulty 2, maybe 3. Owner: QAndrew.

Lua has a `tasks` table. With it, Lua orchestrates: it launches a task, which is in effect a subagent, watches it, steers it with a message, and stops it. All of that needs testing. It has to be airtight before item 9, and other people have to understand it.

**One approach**

This is one way to do it, and a better one is welcome.

- Move the tasks code into a module of its own, or a crate of its own that the Engine uses.
- Write a set of golden markdown files. Each one is a very small prompt that does one thing with tasks.
- Run each one on the Engine with a recorder that logs the effects and events.
- Compare what was logged with the stored output.

**Where it stands**

- The table has twelve functions: `spawn`, `join_any`, `join`, `ready`, `status`, `pending`, `note`, `receive`, `send`, `reply`, `cancel`, and `concurrency`. `tasks.fanout` is defined beside them.
- Roughly 175 tests already cover tasks, fanout, the inbox, and waits. They step a run on one thread with a scripted model.
- The code is spread out: the Lua side is in `__impl_tasks.lua` and `__impl_fanout.lua`, and the scheduler side is across several files.
- The newest part is the inbox: `receive`, `send`, and `reply`.
- Confirm what exists before you write a test for it. `tasks.cancel` stops a task. Starting a canceled task again is listed as planned work.

**Open**

- A module or a crate?
- What does a golden file store and compare: the whole record, or part of it? Items 6 and 7 need the same answer.
- How is the model scripted in a golden test, so that no real inference runs?
- What happens to the tests that exist?

**Read first**

- [Tasks and fanout](https://github.com/cppalliance/runvil-harness/blob/master/decisions/tasks-and-fanout.md), the decision page
- [Tasks](https://github.com/cppalliance/runvil-docs/blob/master/src/language/15-tasks.md) and [fanout](https://github.com/cppalliance/runvil-docs/blob/master/src/language/14-fanout.md) in the guide

### 9. Subagents

Difficulty 3. Owner: Vinnie.

This is the last feature Runvil needs. Subagents give the model the ability to launch tasks, where today only Lua can. It is extremely complicated, and getting it right is crucial. That is why item 8 comes first: when subagents are built, any bug should be in the new code, and not in tasks or anywhere else in the Engine.

This brief is context for the class and not an assignment.

**Where it stands**

- `runvil/subagents` is a built-in Pack that reserves the name. It has no tools.
- Only Lua starts a task today, with `tasks.spawn` or `tasks.fanout`.
- `execute` runs another prompt as a child in the same run, and the caller waits for it. An `execute_async` that returns at once is planned.

### 10. Compaction

Not rated. Owner: TBD.

We are not ready to build this, and nothing gets built now. It is on the list because it is going to be a major item, and people need to start thinking about it.

A conversation grows until it no longer fits the model's context window. Compaction replaces the old part with something smaller. The quality of the compaction affects how well everything performs, and compacting well is not easy.

**The pieces to think about**

- **Getting the data back.** After a compaction, we have to leave instructions behind that tell the model how to get the compacted data.
- **How Cursor does it.** We need to study that.
- **Where the old conversation goes.** A RAG index is one idea. Mounting old conversations into the virtual file system is another. A special tool for the model is a third.
- **Compression.** Should compacted data be compressed with zlib and decompressed on demand?
- **Measurement.** We need benchmarks. After a compaction, we measure how well the model can recall the data.
- **A test harness.** We need to test compaction quickly and easily. Filling a million-token context and running real inference first is not an option. This is probably a separate program with its own infrastructure.

**Where it stands**

- The Engine has the mechanism and no policy. A compactor is a Lua function that the model loop calls when a request no longer fits the context window. It rewrites the section's `messages` with `messages:replace`, and the Engine restores a snapshot when the result breaks a rule.
- Two compactors ship. `compactors.fail` is the default, and it fails the run with `context_exhausted`. `compactors.clear` empties the conversation.
- A compactor may call `models.infer` to ask a model for a summary, and it may call a tool.
- The run log omits compactions. An entry for each one is planned work.

**Read first**

- [Model calls and conversations](https://github.com/cppalliance/runvil-harness/blob/master/decisions/models-and-conversations.md), the decision page, section 6
- [Conversations](https://github.com/cppalliance/runvil-docs/blob/master/src/language/11-conversations.md) in the guide, from "Compactors and context exhaustion"

## Feedback on the prompt language

Vinnie asked Jason what he thinks of the Runvil prompting language approach, compared to Python or other frameworks, and asked for real strengths and weaknesses. This is Jason's reply, kept close to his own words so that we have a record. Every point here gets an answer.

### Advantages

- **code + prose together**
  - it's def better than the orchestrator libraries in Python, LangChain is prob the most popular
  - speaking from experience, code with a bunch of long prompts strings is ugly and harder to maintain
- **security**
  - ephemeral VMs
- **visibility/observability**
  - we control the full stack down to the model on runpod and can add observers anywhere

### Potential challenges

- **composability**
  - I am not clear on how easy/hard this is since we've only been doing single prompts for Agora, but it's super important to get right (and very easy in any pure code programming language)
  - It's tough to work with big files > 2000 lines, but real apps are going to need that much Runvil prompt. Maybe we can consider some convention, like pointing to a directory instead of an md files runs all the md files in the directory in alphabetical order?

### More challenges, from Claude, that Jason agrees with

Jason: "I'd say that composability and any silent failures would be most critical."

- **no cross-file reuse today**
  - `require`/`call`/`prompt.section` only reach sections in the same file, and `execute` is still a "later plan"
  - this is the core of the composability problem, and it pushes people toward the 2000+ line files
- **semantic complexity**
  - the surface looks simple, but there are a lot of rules: pending prose vs commentary, prologue/epilog, the walk falling through into library sections, visibility, scalar returns
  - the language guide is enormous, and some mistakes fail silently instead of loudly: prose that no block reads is dropped as commentary, a fence label typo like `` ```lau `` turns code into prose, and a called section that forgets to return gives `""`
- **errors show up late**
  - section names/paths are resolved at runtime, so a typo in `call("Tempalte")` only fails when that line runs
- **churn**
  - section naming and the whole input contract were redesigned within days of each other
  - fine at this stage, but the spec and guide are large enough that each redesign is expensive, and outside users can't keep up
